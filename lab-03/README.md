# Лабораторна робота 3 — власний DevOps-інструментарій

Автор комітів: **w1xes**. Робота ведеться в окремій гілці й здається через PR у `main`.
Команди нижче виконуються з кореня репозиторію, якщо не вказано інше.

## Резервне копіювання

Потрібні Bash 4+, GNU tar/coreutils, util-linux (`flock`).

```bash
./lab-03/backup.sh --help
./lab-03/backup.sh --source 'my project' --dest '/tmp/my backups' --keep 3
./lab-03/backup.sh --source 'my project' --dest '/tmp/my backups' --keep 3 --dry-run
```

Обов'язкові `--source`, `--dest`; `--keep` типово 5, лише додатне ціле число.
Джерело має бути доступною для читання текою; призначення створюється автоматично.
Призначення всередині джерела та джерело `/` відхиляються, щоб архів не включав сам себе.
Ім'я архіву: `my project-<hash канонічного шляху>-2026-10-20-190000-123456789.tar.gz`.
UTC та наносекунди забезпечують сортування й окремі імена для швидких запусків.
Hash розрізняє різні джерела з однаковим basename. Ротація чіпає лише звичайні
файли відповідного джерела з точним форматом імені. Інші файли й symlink збережені.
Архів спочатку пишеться у тимчасовий файл, потім перейменовується; `flock`
серіалізує одночасні запуски для одного джерела. При помилці tar ротації немає.

Приклад виводу (мітки та розміри залежать від запуску):

```text
Created /tmp/my backups/my project-<hash>-2026-10-20-190000-123456789.tar.gz
2026-10-20T19:00:00Z action=backup result=success archived_files=1 archives_created=1 deleted=1 archive_bytes=170
```

Журнал: stderr і `BACKUP_LOG` (типово `./backup.log`, батьківська тека має існувати).
У dry-run **немає жодних файлових змін**, навіть журналу/lock-файла; журнал і
повний план створення/видалення друкуються в термінал. Dry-run рахує ротацію
з урахуванням майбутнього нового архіву.

Коди: 0 успіх, 2 параметри, 3 джерело, 4 призначення/блокування,
5 архівування, 6 ротація, 7 запис журналу.

### Навіщо `set -euo pipefail`

- `-e`: зупиняє скрипт при неврахованій помилці команди. Без нього після
  невдалого архівування можна було б перейти до видалення старих копій.
- `-u`: звернення до невстановленої змінної — помилка. Без нього друкарська
  помилка в назві шляху перетвориться на порожній рядок і змінить дію команди.
- `pipefail`: конвеєр невдалий, якщо невдала хоча б одна його команда.
  Без нього успішний `wc` приховав би помилку `find` під час підрахунку файлів.

Критичні операції додатково перевіряються явно: `-e` має винятки, зокрема в `if`.

## Монітор API

Python 3.12+, лише стандартна бібліотека. Вхідний формат — JSON:

```json
{"targets": [{"name": "github", "url": "https://github.com", "expected_status": 200,
              "timeout": 10, "threshold_ms": 3000}]}
```

`timeout` — секунди на мережеву операцію, `threshold_ms` — мілісекунди на відповідь.
Цілі й адреси задаються конфігом; секретів у коді/конфігах немає.

```bash
python3 lab-03/api_monitor.py --help
mkdir -p lab-03/var
python3 lab-03/api_monitor.py --config lab-03/config/api.json --output lab-03/var/api.json --no-notify
python3 lab-03/api_monitor.py --config lab-03/config/api-failures.json --output lab-03/var/failures.json --direct --no-notify
```

Для сповіщень задайте **секрет** `API_MONITOR_WEBHOOK` (Slack Incoming Webhook,
HTTPS) через секрети CI/середовища, після чого приберіть `--no-notify`.
Не вставляйте адресу вебхука у Git, аргументи команд або журнали.
Для кожної проблемної цілі надсилається `{"text": "API alert: ... type=dns ..."}`.
Відсутній webhook чи невдала доставка явно відображаються в JSON та коді 4;
`--no-notify` — свідомо обраний діагностичний режим, не доказ доставки у Slack.

Приклад виводу:

```text
dns: dns status=None time_ms=3.1 notification=disabled
refused: connection_refused status=None time_ms=0.4 notification=disabled
expired-certificate: certificate status=None time_ms=80.5 notification=disabled
unexpected-status: unexpected_status status=200 time_ms=65.0 notification=disabled
```

Мережеві помилки `dns`, `connection_refused`, `timeout`, `certificate`, `network`
повторюються рівно один раз. Неправильний HTTP-код і повільна правильна відповідь
не повторюються. Перевіряються всі цілі. TLS-перевірка завжди увімкнена.
`--direct` вимикає проксі **лише для цілей**: інакше помилка DNS або сертифіката
може бути прихована відповіддю проксі. Потрібен дозволений прямий мережевий доступ.
Public demo використовує спеціальний `.invalid`, закритий локальний порт,
[expired.badssl.com](https://expired.badssl.com/) і `example.com` з очікуванням 201.
Це навмисні помилки; доступ до цих доменів залежить від мережевої політики.

Звіт атомарно записується в `--output` (батьківська тека має існувати): час UTC,
ціль, HTTP status/null, response_ms, failure_type/null, healthy, attempts, notification.
Журнал — JSONL у stderr і `TOOLKIT_LOG` (типово `lab-03/var/toolkit.jsonl`).
Кожен запуск, включно з довідкою та помилкою параметрів, має початок/результат.
Коди: 0 усі здорові, 1 проблемна ціль, 2 параметри/конфіг, 3 файловий I/O,
4 немає сповіщення/помилка доставки, 130 переривання. Код 4 має пріоритет над 1;
окремі причини інцидентів завжди є в структурованому звіті.

### Відмова з'єднання проти тайм-ауту

`connection_refused` означає, що стек мережі повернув явну відмову: наприклад,
процес не слухає порт або firewall активно відхиляє запит. Спочатку перевіряю
процес, адресу bind, номер порту й правила reject. Тайм-аут означає, що в межах
часу не завершилась операція: пакети можуть губитися/відкидатися, маршрут може
бути порушений, а сервер — перевантажений. Тут перевіряю маршрути, drop-правила,
затримки й ресурси сервера. Збільшення тайм-ауту не виправить відсутній listener.
DNS відбувається до з'єднання, перевірка сертифіката — після TCP під час TLS,
а неправильний код/повільна відповідь показують, що HTTP уже працює.

Офлайн-тести піднімають справжні локальні HTTP/TLS-сервери, перевіряють
закритий порт, затримку, неочікуваний код і відмову довіри TLS. DNS та прострочення
додатково перевіряються контрольованими винятками; Slack payload приймає локальний
тестовий сервер. Жоден тест не потребує реального Slack-секрета.
