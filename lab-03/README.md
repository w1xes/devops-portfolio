# Лабораторна робота 3 — власний DevOps-інструментарій

Автор комітів: **w1xes**. Робота ведеться в окремій гілці й здається через PR у `main`.
Команди нижче виконуються з кореня репозиторію, якщо не вказано інше.

## Резервне копіювання

Потрібні Bash 4+, GNU tar/coreutils, util-linux (`flock`).

```bash
./lab-03/backup.sh --help
./lab-03/backup.sh --source 'my project' --dest '/tmp/my backups' --keep 3
./lab-03/backup.sh --source 'my project' --dest '/tmp/my backups' --keep 3 --dry-run
```

Обов'язкові `--source`, `--dest`; `--keep` типово 5, лише додатне ціле число.
Джерело має бути доступною для читання текою; призначення створюється автоматично.
Призначення всередині джерела та джерело `/` відхиляються, щоб архів не включав сам себе.
Ім'я архіву: `my project-<hash канонічного шляху>-2026-10-20-190000-123456789.tar.gz`.
UTC та наносекунди забезпечують сортування й окремі імена для швидких запусків.
Hash розрізняє різні джерела з однаковим basename. Ротація чіпає лише звичайні
файли відповідного джерела з точним форматом імені. Інші файли й symlink збережені.
Архів спочатку пишеться у тимчасовий файл, потім перейменовується; `flock`
серіалізує одночасні запуски для одного джерела. При помилці tar ротації немає.

Приклад виводу (мітки та розміри залежать від запуску):

```text
Created /tmp/my backups/my project-<hash>-2026-10-20-190000-123456789.tar.gz
2026-10-20T19:00:00Z action=backup result=success archived_files=1 archives_created=1 deleted=1 archive_bytes=170
```

Журнал: stderr і `BACKUP_LOG` (типово `./backup.log`, батьківська тека має існувати).
У dry-run **немає жодних файлових змін**, навіть журналу/lock-файла; журнал і
повний план створення/видалення друкуються в термінал. Dry-run рахує ротацію
з урахуванням майбутнього нового архіву.

Коди: 0 успіх, 2 параметри, 3 джерело, 4 призначення/блокування,
5 архівування, 6 ротація, 7 запис журналу.

### Навіщо `set -euo pipefail`

- `-e`: зупиняє скрипт при неврахованій помилці команди. Без нього після
  невдалого архівування можна було б перейти до видалення старих копій.
- `-u`: звернення до невстановленої змінної — помилка. Без нього друкарська
  помилка в назві шляху перетвориться на порожній рядок і змінить дію команди.
- `pipefail`: конвеєр невдалий, якщо невдала хоча б одна його команда.
  Без нього успішний `wc` приховав би помилку `find` під час підрахунку файлів.

Критичні операції додатково перевіряються явно: `-e` має винятки, зокрема в `if`.

## Монітор API

Python 3.12+, лише стандартна бібліотека. Вхідний формат — JSON:

```json
{"targets": [{"name": "github", "url": "https://github.com", "expected_status": 200,
              "timeout": 10, "threshold_ms": 3000}]}
```

`timeout` — секунди на мережеву операцію, `threshold_ms` — мілісекунди на відповідь.
Цілі й адреси задаються конфігом; секретів у коді/конфігах немає.

```bash
python3 lab-03/api_monitor.py --help
mkdir -p lab-03/var
python3 lab-03/api_monitor.py --config lab-03/config/api.json --output lab-03/var/api.json --no-notify
python3 lab-03/api_monitor.py --config lab-03/config/api-failures.json --output lab-03/var/failures.json --direct --no-notify
```

Для сповіщень задайте **секрет** `API_MONITOR_WEBHOOK` (Slack Incoming Webhook,
HTTPS) через секрети CI/середовища, після чого приберіть `--no-notify`.
Не вставляйте адресу вебхука у Git, аргументи команд або журнали.
Для кожної проблемної цілі надсилається `{"text": "API alert: ... type=dns ..."}`.
Відсутній webhook чи невдала доставка явно відображаються в JSON та коді 4;
`--no-notify` — свідомо обраний діагностичний режим, не доказ доставки у Slack.

Приклад виводу:

```text
dns: dns status=None time_ms=3.1 notification=disabled
refused: connection_refused status=None time_ms=0.4 notification=disabled
expired-certificate: certificate status=None time_ms=80.5 notification=disabled
unexpected-status: unexpected_status status=200 time_ms=65.0 notification=disabled
```

Мережеві помилки `dns`, `connection_refused`, `timeout`, `certificate`, `network`
повторюються рівно один раз. Неправильний HTTP-код і повільна правильна відповідь
не повторюються. Перевіряються всі цілі. TLS-перевірка завжди увімкнена.
`--direct` вимикає проксі **лише для цілей**: інакше помилка DNS або сертифіката
може бути прихована відповіддю проксі. Потрібен дозволений прямий мережевий доступ.
Public demo використовує спеціальний `.invalid`, закритий локальний порт,
[expired.badssl.com](https://expired.badssl.com/) і `example.com` з очікуванням 201.
Це навмисні помилки; доступ до цих доменів залежить від мережевої політики.

Звіт атомарно записується в `--output` (батьківська тека має існувати): час UTC,
ціль, HTTP status/null, response_ms, failure_type/null, healthy, attempts, notification.
Журнал — JSONL у stderr і `TOOLKIT_LOG` (типово `lab-03/var/toolkit.jsonl`).
Кожен запуск, включно з довідкою та помилкою параметрів, має початок/результат.
Коди: 0 усі здорові, 1 кілька різних типів збою, 2 параметри/конфіг,
3 файловий I/O, 4 немає сповіщення/помилка доставки, 10 DNS, 11 відмова,
12 тайм-аут, 13 сертифікат, 14 неочікуваний код, 15 повільна відповідь,
16 інша мережева помилка, 130 переривання. Код 4 має пріоритет над діагностичними кодами;
окремі причини інцидентів завжди є в структурованому звіті.

### Відмова з'єднання проти тайм-ауту

`connection_refused` означає, що стек мережі повернув явну відмову: наприклад,
процес не слухає порт або firewall активно відхиляє запит. Спочатку перевіряю
процес, адресу bind, номер порту й правила reject. Тайм-аут означає, що в межах
часу не завершилась операція: пакети можуть губитися/відкидатися, маршрут може
бути порушений, а сервер — перевантажений. Тут перевіряю маршрути, drop-правила,
затримки й ресурси сервера. Збільшення тайм-ауту не виправить відсутній listener.
DNS відбувається до з'єднання, перевірка сертифіката — після TCP під час TLS,
а неправильний код/повільна відповідь показують, що HTTP уже працює.

Офлайн-тести піднімають справжні локальні HTTP/TLS-сервери, перевіряють
закритий порт, затримку, неочікуваний код і відмову довіри TLS. DNS та прострочення
додатково перевіряються контрольованими винятками; Slack payload приймає локальний
тестовий сервер. Жоден тест не потребує реального Slack-секрета.

## Бонус 1: стан Linux-машини

```bash
./lab-03/monitor.sh --help
MONITOR_LOG=lab-03/var/monitor.log ./lab-03/monitor.sh
MEM_MAX=0 MONITOR_LOG=lab-03/var/forced.log ./lab-03/monitor.sh  # очікується код 11
PROCESSES=$'bash\npython3' ./lab-03/monitor.sh
SERVICES=$'sshd.service\nnginx.service' ./lab-03/monitor.sh
```

`--config FILE` вибирає **довірений shell-конфіг** (виконується через `source`),
типово `config/monitor.env` біля скрипта. Пороги задані там, не в логіці скрипта;
експортовані змінні мають пріоритет. `CPU_MAX`, `MEM_MAX` — максимум використання,
`DISK_MIN_FREE` — мінімум вільного місця, від 0 до 100. `SAMPLE_SECONDS` — інтервал
CPU (0..60 секунд, типово 0.2). `DISK_PATHS`, `PROCESSES`, `SERVICES` — списки
через новий рядок; порожні процеси/сервіси означають, що їх не перевіряємо.
Шлях з пробілами передавайте одним рядком у `DISK_PATHS`.

CPU — різниця лічильників `/proc/stat`, idle включає iowait, guest не рахується
вдруге; RAM — `(MemTotal-MemAvailable)/MemTotal`; диск — вільний відсоток з `df`.
Для процесів використовується точне ім'я `comm` через `pgrep -x` (Linux обмежує
його 15 символами), для сервісів — `systemctl is-active` (потрібен systemd).
Коди: 0 норма, 1 кілька типів спрацювання, 2 конфіг, 3 OS/метрики/журнал,
10 CPU, 11 RAM, 12 диск, 13 сервіс, 14 процес. Журнал — stdout і `MONITOR_LOG` (типово `./monitor.log`).
Кожен рядок містить UTC, дію й результат та підходить для cron.

```text
2026-10-20T19:00:00Z action=system_monitor metric=memory_used_pct value=12.30 max=0 result=ALERT
2026-10-20T19:00:00Z action=system_monitor result=finished exit_code=11
```

### Розклад

У `config/monitor.crontab` є щохвилинний розклад. Замініть абсолютний шлях,
створіть `lab-03/var` і додайте рядки до **наявного** `crontab -e`, не затираючи
інші завдання. Cron має мати доступ до Bash, awk, df, date, sleep, pgrep.
Перевіряйте `tail lab-03/var/monitor-cron.log`; `cron-output.log` зберігає stderr.

У контейнері без системного cron можна використати
[Supercronic](https://github.com/aptible/supercronic), який виконує звичайний
crontab без root. Наприклад, після встановлення `supercronic`:

```bash
mkdir -p lab-03/var
sed "s|/absolute/path/devops-portfolio|$PWD|g" lab-03/config/monitor.crontab > lab-03/var/monitor.crontab
supercronic -test lab-03/var/monitor.crontab
supercronic lab-03/var/monitor.crontab
```

Цей приклад припускає шлях без пробілів, `%`, `|`, `&`; для іншого шляху
відредагуйте crontab вручну з коректним shell/cron-екрануванням.
Процес scheduler має працювати постійно; після відновлення контейнера його слід
запустити знову. На звичайному сервері cron запускається системною службою.

## Бонус 2: аналіз Combined access log

```bash
python3 lab-03/log_analyzer.py --help
python3 lab-03/log_analyzer.py --input lab-03/tests/fixtures/access.combined --output /tmp/report.json --format json --top 3
python3 lab-03/log_analyzer.py --input lab-03/tests/fixtures/access.combined --output /tmp/report.txt --format text --top 3
```

`--input`, `--output` обов'язкові; `--format text|json` (типово text),
`--top N` (типово 10, додатне). Вхід і вихід мають бути різними файлами;
батьківська тека звіту має існувати. Обробка потокова: у пам'яті лічильники,
а не весь файл. Підтримуються IPv4/IPv6, escaped лапки, розмір `-`.
Некоректні IP, дати, статуси та пошкоджені рядки пропускаються й рахуються.
Години нормалізуються в UTC з урахуванням початкового timezone.
Топ має стабільний порядок при однакових лічильниках; усі пікові години
з однаковим максимумом потрапляють до звіту.

Приклад на синтетичному fixture (адреси з документаційних діапазонів):

```text
Valid lines: 4
Malformed lines: 2
Top addresses:
  192.0.2.10: 2
  198.51.100.2: 1
  2001:db8::1: 1
```

У повному звіті також є всі класи 1xx..5xx, запити за годинами та пік:
`2026-10-20T07:00:00Z`, 3 запити. Коди: 0 звіт створено (пошкоджені рядки
не є фатальними), 2 параметри, 3 читання/запис. Журнал — спільний `TOOLKIT_LOG`.
Тести перевіряють валідний/невалідний рядок, IPv6, escaped лапки, порожній файл,
UTC-агрегацію, топ і кількість пошкоджених рядків.

## Бонус 3: Go file organizer

Модуль `lab-03/organizer`, Go 1.24+. Збірка **статичного** Linux-бінарника:

```bash
mkdir -p lab-03/bin
(cd lab-03/organizer && CGO_ENABLED=0 go build -trimpath -ldflags='-s -w' -o ../bin/organizer .)
file lab-03/bin/organizer
./lab-03/bin/organizer --help
./lab-03/bin/organizer categories
./lab-03/bin/organizer organize --source '/tmp/my files' --dry-run
./lab-03/bin/organizer organize --source '/tmp/my files'
(cd lab-03/organizer && go test -v ./...)
```

Підкоманди: `categories`, `organize`; остання потребує `--source DIR`, має
`--dry-run` і `--help`. Розкладка: `documents`, `images`, `videos`, `archives`.
Повний список розширень показує `categories`; регістр розширення не важливий.
Не обходить вкладені теки, невідомі типи й symlink пропускає. Категорія-symlink
відхиляється. Колізії перевіряються до змін; на етапі перенесення `link+unlink`
також не перезаписує наявний файл. Потрібна файлова система з hard links;
перенесення між різними filesystem не підтримується. У разі I/O помилки посеред
кількох перенесень попередні успішні перенесення лишаються виконаними.
Повторний запуск без нових файлів дає `files=0`.

```text
MOVE "/tmp/my files/report.pdf" -> "/tmp/my files/documents/report.pdf"
files=1 dry_run=true
```

Коди: 0 успіх, 2 аргументи, 3 джерело, 4 колізія/призначення/перенесення,
5 журнал. JSONL журнал — stderr і `ORGANIZER_LOG` (типово `./organizer.log`).
Dry-run друкує журнал лише в stderr і не змінює файлову систему.

### Порівняння зі скриптом

`organizer_reference.py` — працездатний Python-аналог із тими ж категоріями,
перевіркою колізій, підкомандами й dry-run. Приклад:

```bash
python3 lab-03/organizer_reference.py organize --source '/tmp/my files' --dry-run
python3 lab-03/benchmark_startup.py --help
python3 lab-03/benchmark_startup.py --output /tmp/startup-benchmark.json --runs 30
```

Фактичні розміри та часи цього середовища збережено в
[evidence/startup-benchmark.json](evidence/startup-benchmark.json): 30 послідовних
запусків `--help`, 3 прогрівочні запуски виключені, stdout/stderr і журнали
направлені в `/dev/null`. Це вимір запуску CLI, а не швидкості переміщення файлів.
Розмір Python — лише джерело, **без інтерпретатора і стандартної бібліотеки**;
Go-бінарник містить runtime і за `file` є `statically linked`.

Go зручний для поширення одного файла на чисті машини без встановлення Python,
для частих коротких запусків і програм, яким важлива продуктивність. Скрипт
менший як вихідний файл, його швидше змінити й прочитати на сервері, де Python
уже є. Go потребує окремої збірки для кожних OS/архітектури; статичність не
робить Linux-бінарник переносним на Windows. Часи залежать від навантаження,
версій і кешів; порівнювати варто на одній машині за однаковою методикою.

## Встановлення залежностей і Git-хуків

На Linux x86-64/ARM64 з Python 3.12+, curl, tar, sha256sum, openssl, util-linux,
procps, GNU coreutils і make:

```bash
./lab-03/dev-setup.sh
source lab-03/activate.sh
./lab-03/check.sh
```

`dev-setup.sh` створює `.venv`, ставить зафіксовані Ruff/ShellCheck та Go 1.27.3
з перевіркою SHA-256 офіційного архіву. Також ставить Supercronic v0.2.34 через
Go modules (перевірка модульних сум збережена). SHA-256 взяті з офіційного
`https://go.dev/dl/?mode=json`. Системні пакети й налаштування не змінюються.
Ні приватні ключі, ні runtime-журнали, ні бінарники не комітяться.
`source lab-03/activate.sh` потрібний у кожному новому shell; це особливо важливо,
якщо системна команда `go` є грою GNU Go, а не компілятором.
Якщо інструменти вже є, достатньо Python 3.12+, Go 1.24+ і пакетів із
`requirements-dev.txt`; скрипти прикладних утиліт не залежать від pip-пакетів.

Встановіть версійовані хуки з кореня репозиторію:

```bash
git config --local core.hooksPath lab-03/hooks
./lab-03/hooks/pre-commit --help
./lab-03/hooks/pre-push --help
```

Це локальне налаштування: після нового clone його треба повторити.
Перед зміною наявного `core.hooksPath` перевірте `git config --get core.hooksPath`
і збережіть свої сторонні хуки. Щоб скасувати нашу конфігурацію:
`git config --local --unset core.hooksPath` (або поверніть попереднє значення).

`pre-commit` бере NUL-розділений список staged AC/M/R-файлів і витягує їхні
**blob з індексу** у тимчасову теку. Видалені файли, symlink і решта репозиторію
не лінтяться. ShellCheck застосовується до Bash, Ruff — до Python, включно
з файлами без розширення з відповідним shebang. Ruff має однаковий явний набір
правил `E4,E7,E9,F,I` у хуку й `pyproject.toml`. Частково staged файл перевіряється
у тій версії, яка потрапить у коміт; виправлення лише у working tree не врятує
поганий staged blob. Відсутній потрібний лінтер також блокує коміт.

`pre-push` запускає `run-tests.sh`: Python unittest та Go tests. Невдала перевірка
повертає 1 і блокує push; відсутній runner — 3, неправильний ручний виклик — 2.
Журнал — stderr та `PRE_PUSH_LOG` (типово `lab-03/var/pre-push.log`);
`--help` має запис у stderr. Прекоміт має спільний JSONL `TOOLKIT_LOG`.
Аргументи remote URL не записуються в журнал.

### Чому хуки не є контролем

Хук живе на машині автора. Його можна видалити, не встановити або обійти через
`git commit --no-verify` / `git push --no-verify`. Він дає швидкий зворотний зв'язок,
але не доводить іншому учаснику, що код перевірено. CI у
`.github/workflows/lab-03.yml` заново отримує коміт і виконує лінтери, всі тести,
`go vet`, перевірку gofmt та статичну збірку незалежно від локальних хуків.

Щоб ці перевірки **обов'язково** блокували злиття, власник репозиторію має
увімкнути GitHub ruleset/branch protection для `main`: require pull request,
require status check **lint-test-build** з workflow **Lab 03**, вимкнути обхід
правил для звичайних учасників. Один YAML не вмикає branch protection автоматично.
Обмеження push/merge застосовує GitHub, а не скрипт на машині автора.

## Повний прогін та докази

```bash
source lab-03/activate.sh
./lab-03/check.sh
python3 lab-03/demo_api.py --help
python3 lab-03/demo_api.py --output-dir lab-03/var/acceptance
```

`demo_api.py` піднімає локальні HTTP/TLS-сервери й утримує закритий TCP-порт.
Тимчасова CA підписує leaf із датою закінчення 2020-01-02. OpenSSL окремо
підтверджує саме прострочення; Python довіряє лише тестовій CA через
`SSL_CERT_FILE` дочірнього процесу, **перевірка TLS не вимикається**. Ключі
видаляються разом із тимчасовою текою. Четверта ціль — `.invalid`, гарантовано
неіснуючий домен. Демонстратор очікує чотири різні failure_type та код 1
монітора, а сам завершується 0 лише після перевірки цих очікувань.

Мережевий timeout urllib обмежує socket-операції, а не роботу системного DNS
resolver; тому DNS може тривати довше за `timeout`. Прямий доступ до публічних
доменів у хмарному контейнері може бути заборонений; локальний демонстратор
відтворює чотири випадки без залежності від зовнішніх HTTP-сервісів.

Матеріали в `evidence/` містять фактичні результати, окремо від прикладів вище.
Розклад перевірено Supercronic на п'яти щохвилинних запусках; після перевірки
запущений для демонстрації scheduler зупинено. Реальні пороги Linux у контейнері
стосуються видимих `/proc`-метрик хоста, а не cgroup CPU/RAM-квоти контейнера.
Зовнішню доставку в особистий Slack слід перевірити після додавання власного
`API_MONITOR_WEBHOOK`; тести перевіряють справжній HTTP POST до локального
приймача з таким самим Slack JSON payload.

## Що пояснити на захисті

Чому ротація ізольована hash шляху; чому тимчасовий архів публікується лише
після успішного tar; чому dry-run не створює журналу; на якому етапі мережі
виникає кожен збій; навіщо retry лише для мережевої помилки; чому мілісекунди
порога відрізняються від секунд timeout; чому лінтимо index, а не working tree;
чому обов'язковість CI потребує branch protection; чому Go-бінарник більший,
але запускається без встановленого інтерпретатора.
