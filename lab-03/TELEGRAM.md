# Telegram-бот для моніторингу API

Бот замінює Slack-сповіщення. Працює на Linux із Python 3.12+ зі стандартною бібліотекою (для блокування — flock).
Використовує [Telegram Bot API](https://core.telegram.org/bots/api) і long polling:
вхідний HTTP-порт, домен і зовнішній webhook для нього не потрібні.
Потрібен вихідний HTTPS-доступ до `api.telegram.org` і до API з конфігурації.

## Підключення власного бота

1. У [@BotFather](https://t.me/BotFather) виконайте `/newbot`, задайте ім'я та username.
2. Збережіть виданий токен як секрет `TELEGRAM_BOT_TOKEN` у налаштуваннях середовища.
   Не надсилайте токен у чат з асистентом і не записуйте в Git/аргументи команд.
3. Після застосування налаштувань визначте ID свого чату:

```bash
cd /workspace/devops-portfolio
source lab-03/activate.sh
python3 lab-03/telegram_bot.py --discover-chat
```

Надішліть `/start` своєму боту у **приватному чаті**. Після запуску discovery надішліть новий `/start`; старі повідомлення пропускаються.
Команда покаже кандидата
`TELEGRAM_CHAT_ID`. Підтвердьте, що це саме ваш чат, і додайте число в змінні
середовища під цією назвою. Визначення ID нічого не надсилає, не призначає власника
автоматично й не записує токен. Воно очікує до 120 секунд. Не запускайте discovery
одночасно з іншим polling-процесом цього ж бота.

У звичайному локальному терміналі секрет можна ввести без відображення символів:

```bash
read -rsp 'Telegram token: ' TELEGRAM_BOT_TOKEN; export TELEGRAM_BOT_TOKEN; printf '\n'
read -rp 'Telegram chat ID: ' TELEGRAM_CHAT_ID; export TELEGRAM_CHAT_ID
```

Для Codex cloud використовуйте захищені налаштування середовища. Збереження
чернетки не додає значення й не запускає бота: зміни треба застосувати та
опублікувати через інтерфейс середовища.

4. Перевірте доставку й запустіть бот:

```bash
python3 lab-03/telegram_bot.py --test-message
python3 lab-03/telegram_bot.py --config lab-03/config/api.json --interval 60
```

`--test-message` надсилає одне діагностичне повідомлення і завершується.
Звичайний запуск одразу перевіряє API, потім працює до Ctrl+C або SIGTERM.
Початковий інтервал — 60 секунд; наступна автоматична перевірка планується після
завершення попередньої, без паралельних прогонів і накопичення пропущених запусків.
Бот працює лише доки запущений його процес. Для постійної роботи потрібна служба.

## Команди в Telegram

| Команда | Дія |
|---|---|
| `/start`, `/help` | Довідка |
| `/status` | Останні результати, час UTC, інтервал і стан розкладу |
| `/check` | Перевірити всі API зараз, навіть під час паузи |
| `/targets` | Імена цілей, очікувані коди, timeout і пороги |
| `/pause` | Призупинити автоматичні перевірки |
| `/resume` | Відновити їх; наступний прогін виконується одразу |
| `/interval 120` | Установити інтервал 120 секунд; межі 10..86400 |
| `/chatid` | Показати ID дозволеного чату |

Меню команд реєструється автоматично лише для налаштованого чату.
У групі підтримується форма `/check@username_бота`. Команди для іншого бота
ігноруються. Невідомі команди отримують довідкову відповідь.

Дозвіл визначається **точним числовим chat ID**. Повідомлення з інших чатів
ігноруються без відповіді й не можуть запустити перевірку або прочитати звіт.
Для особистого використання налаштуйте приватний чат. Якщо навмисно вказати ID
групи, право команд матимуть її учасники: це авторизація чату, а не окремих людей.
Цілі змінюються тільки в JSON-файлі; бот не приймає довільні URL або shell-команди.

## Сповіщення й відновлення

При першому збої надходить повідомлення на зразок:

```text
🚨 Проблема API: github
Тип: timeout — Тайм-аут
HTTP: немає відповіді
Час: 10002.7 мс
Спроб: 2
Перевірено (UTC): 2026-10-27T16:00:00.000+00:00
```

Монітор зберігає всі шість типів збою лабораторної: DNS, відмова з'єднання,
тайм-аут, TLS-сертифікат, неочікуваний HTTP-код, повільна відповідь.

Автоматичний бот надсилає повідомлення при першій проблемі, зміні типу збою або
HTTP-коду, а потім окреме `✅ API відновився`. Однакові повтори приглушуються;
зміна лише тривалості відповіді не є новим інцидентом. Відсутній/невдалий
`sendMessage` не позначається як успішна доставка, тому наступний прогін спробує
ще раз. Для довгих звітів текст ділиться на частини з урахуванням Unicode.
`/check` також використовує приглушення інцидентів, але завжди повертає звіт.

Одноразовий CLI, як і раніше, надсилає окреме повідомлення для **кожної**
проблемної цілі за запуск — це вимога основної лабораторної:

```bash
mkdir -p lab-03/var
python3 lab-03/api_monitor.py --config lab-03/config/api.json --output lab-03/var/api.json
# Лише діагностика без надсилання:
python3 lab-03/api_monitor.py --config lab-03/config/api.json --output lab-03/var/api.json --no-notify
```

Здоровий результат без сповіщення має `notification=not_needed`. Для проблемного:
`sent`, `failed`, `missing_telegram_config` або `disabled`. У боті додатково є
`unchanged` та `recovery_sent`; проміжне `pending` означає ще не завершену доставку.
Результати API записуються до спроби надсилання й оновлюються після неї.
Код CLI 4 означає, що повідомлення не було доставлено; фактична причина збою API
все одно лишається у звіті.

## Файли стану й параметри

Повний перелік: `python3 lab-03/telegram_bot.py --help`.

| Параметр | Типове значення |
|---|---|
| `--config` | `lab-03/config/api.json` |
| `--output` | `lab-03/var/telegram-results.json` |
| `--state` | `lab-03/var/telegram-state.json` |
| `--interval` | 60 секунд для нового стану |
| `--paused` | Почати на паузі, тільки для нового стану |
| `--direct` | Обходити проксі лише для API-цілей; Telegram використовує звичайний HTTPS-маршрут |

Збережений стан має пріоритет над початковими `--interval` і `--paused`.
Він містить offset Telegram updates, паузу, інтервал, підтверджені сповіщення та
числові bot/chat ID, але **не токен і не URL цілей**. Конфіг перечитується на кожній
перевірці; зміна цілі створює нову історію її інциденту. JSON записується атомарно,
файли створюються з доступом лише власника. Копіюйте стан для резервування.
При пошкодженні він не стирається автоматично — відновіть справну копію.
Не використовуйте однаковий шлях для конфігурації, звіту та стану.

Один state-файл захищено локальним flock; два процеси одного бота з різними
state-файлами також можуть конфліктувати через Telegram `getUpdates`. Запускайте
один polling-процес на токен. Зміна bot/chat ID потребує окремого нового state-файла,
щоб старий offset та приглушені сповіщення не переходили до іншого бота/одержувача.

Offset підтверджується після обробки update. При аварії між відправленням і
записом стану можливе повторне повідомлення: exactly-once Telegram не гарантує.
Long polling очікує до 20 секунд, мережевий запит має додатковий запас 10 секунд;
Ctrl+C/SIGTERM коректно завершують цикл після поточного запиту/перевірки.
Тривала перевірка цілей може затримати відповіді на команди.

Коди бота: 0 штатне завершення/успішна діагностика, 2 параметри або конфіг,
3 I/O/стан/журнал, 4 Telegram API, 5 зайнятий state-файл. Відмова 401/403 або
конфлікт 409 зупиняють бота з поясненням без секретів. Тимчасові мережеві помилки
повторюються з паузою, 429 враховує `retry_after` (1..300 секунд).
Якщо вже налаштований Telegram webhook, бот відмовиться від polling і попросить
видалити webhook; він не змінює чужі налаштування автоматично.

## Постійна служба Linux

Приклад [deploy/devops-telegram@.service](deploy/devops-telegram@.service) призначено
для сервера із systemd. Він не встановлюється автоматично в хмарний контейнер.
Припускається, що checkout і `.venv` підготовлені в `/opt/devops-portfolio`, а
звичайний користувач служби має доступ до читання коду та запуску Python.
Замініть `YOUR_LINUX_USER` на наявний Linux-акаунт; GitHub username сам по собі
не створює такого системного користувача.

Адміністратор має створити `/etc/devops-telegram/YOUR_LINUX_USER.env` з правами 600
і заповнити його через захищений редактор:

```text
TELEGRAM_BOT_TOKEN=значення_із_BotFather
TELEGRAM_CHAT_ID=числовий_ID
```

Не перезаписуйте наявний env-файл без перевірки. Потім:

```bash
sudo install -m 644 lab-03/deploy/devops-telegram@.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now devops-telegram@YOUR_LINUX_USER.service
sudo systemctl status devops-telegram@YOUR_LINUX_USER.service
sudo journalctl -u devops-telegram@YOUR_LINUX_USER.service -f
```

Systemd створить приватні каталоги `/var/lib/devops-telegram-YOUR_LINUX_USER` для
стану та `/var/log/devops-telegram-YOUR_LINUX_USER` для JSONL-журналу. Служба
запускається без root, відновлюється після тимчасової помилки процесу й отримує
SIGTERM при `systemctl stop`. Коди конфігурації/доступу 2, 4, 5 не перезапускаються
нескінченно. Для розгортання на іншому шляху відредагуйте unit до встановлення.

## Перевірки без справжнього токена

```bash
source lab-03/activate.sh
./lab-03/check.sh
```

Тести використовують фіктивний токен і справжній локальний HTTPS-сервер із
явно довіреним тестовим сертифікатом. Повний бот запускається окремим процесом:
проходить getMe, реєстрацію меню, getUpdates, авторизовані команди, alert,
відновлення та завершення через SIGTERM. Додатково перевірено чужий chat ID,
приглушення повторів, перезапуски, пошкоджений стан, rate limits і відсутність
токена в журналах. TLS-верифікація увімкнена, редиректи для Bot API заборонені.
Це перевірка реалізації; реальне підключення до вашого бота підтверджується
`--test-message` після додавання секрету й chat ID.
