# Фактичні результати перевірок

Ці матеріали отримано під час виконання команд у хмарному Linux-середовищі.
Початкові файли від 2026-10-20 збережено як історичні докази першої версії.
Після переходу на Telegram актуальний прогін — [telegram-checks.txt](telegram-checks.txt):
**54 Python-тести та 3 Go-тести**, лінтери, go vet, gofmt і статична збірка.
Автоматичні тести використовують фіктивний токен. Окремо 2026-10-27 перевірено
живий Telegram getMe через налаштований HTTPS-проксі зі справжнім секретним
binding; авторизація успішна. Доставка в особистий чат потребує TELEGRAM_CHAT_ID.
Час у журналах — UTC. Це локальна перевірка, не результат GitHub Actions.

Go-бінарник у вимірі: 2 678 944 байти, медіана запуску **1.190 мс**.
Python-аналог: 3 637 байтів джерела без інтерпретатора, медіана **28.968 мс**.
Це вимір `--help` у цьому середовищі, без твердження про універсальну перевагу.

Тест `test_real_untrusted_tls_certificate` спочатку перевіряє відмову довіри TLS,
а потім, із явно довіреним локальним сертифікатом, повністю запускає CLI монітора
й отримує `notification=sent` через HTTPS. Тестовий приймач отримує Slack payload;
секретний шлях webhook не потрапляє до stdout/stderr/JSONL. Це перевірка протоколу
сповіщення, не повідомлення до зовнішнього особистого Slack.

Публічний `api-failures.json` також запускали, але прямий DNS до зовнішніх доменів
у контейнері обмежений: це не доказ перевірки публічного простроченого сертифіката.
Натомість локальний acceptance demo створює CA та **справді прострочений** leaf,
підтверджує його прострочення OpenSSL і перевіряє його через звичайну TLS-верифікацію.
Тимчасові приватні ключі знищено; у репозиторії їх немає.


## Оновлення Telegram

Повна реалізація тестується процесом бота проти локального HTTPS Bot API:
getMe, getWebhookInfo, setMyCommands, getUpdates, sendMessage, команди,
автоперевірка, перше сповіщення, відновлення та SIGTERM. Тестовий сертифікат
явно довірений лише дочірньому процесу; перевірка TLS залишається ввімкненою.
Чужий chat ID не запускає команди та не отримує повідомлень.

Окремо перевірено приглушення повторів, невдалу доставку з повтором наступного
прогону, offset після перезапуску, прив'язку стану до bot/chat ID, збереження
паузи/інтервалу, rate limit 429 та очікування retry_after, блокування другого
процесу, пошкоджений JSON-стан і відсутність токена у звітах/журналах/помилках.
Discovery пропускає старі /start і не авторизує кандидата автоматично.

Шаблон systemd перевірено `systemd-analyze verify` на тимчасовій копії unit із
шляхом `/opt/devops-portfolio`, заміненим на існуючий `/workspace/devops-portfolio`.
Це статична перевірка unit, а не запущена системна служба в контейнері.
Звернення до `https://api.telegram.org` без токена повернуло HTTP 302 і підтвердило
мережевий маршрут; це не підтверджує авторизацію конкретного бота чи доставку.


Після підключення живого секрету додано регресійний тест для непрозорих
proxy-backed markers: вони передаються без перетворення до фіксованого
`api.telegram.org`, де проксі підставляє токен. Формат буквального BotFather
токена не використовується як доказ валідності службового binding.
Оновлений [telegram-checks.txt](telegram-checks.txt) містить 54 Python-тести.
